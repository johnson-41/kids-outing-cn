# 活动数据源：全国怎么查当周有什么

规则层不绑城市，活动层每次都变。这份文件只管一件事：**当周的活动去哪查、查不到怎么写。**

## 一、为什么单列一份

场馆的开放时间和门票，一年查一次就够。活动不行：一个展览这周在办，下周就撤；一个市集只开两天。

所以城市资料只存「去哪找」，不存「有什么」。存下来的一定会过期，而且过期了还容易被当成事实引用。

## 二、三层渠道

### 第一层：主办方本体

优先级最高。具体是哪种主办方，决定查哪里：

| 主办方 | 查哪里 |
|---|---|
| 博物馆、科技馆、美术馆 | 官方公众号或小程序；官网「展览」「活动」栏目 |
| 图书馆、文化馆、少年宫 | 官方公众号；当地文旅局的公共文化服务页面 |
| 公园、景区 | 公园管理处公众号；市城管或林业园林局的公告 |
| 商业场馆（乐园、水乐园、攀岩馆） | 官方公众号或小程序；官方票务页 |
| 高校、科研机构 | 学校官网或学院公众号；开放日的单独公告 |
| 社区、街道 | 街道办公众号；社区公告栏照片（需现场核实） |

**判定标准**：能给出起止日期、能给出预约入口、能说明适用对象。三条都有的，才算主办方原始页。

### 第二层：本地官方发布

当地文旅局、教育局、体育局、科协的公众号与官网。用来发现主办公众号没推送的活动，例如免费开放日、公益讲座、科普周。

这一层的价值是覆盖面，不是精确度。看到线索后回第一层核。

### 第三层：聚合与体验

本地生活号、活动聚合站、社交平台的本地话题。只用来发现，不作为依据。

判定三条，命中两条即弃用：

1. 无发布日期。
2. 无主办方名称。
3. 通篇「建议提前规划」式空话，店名对不上地址。

## 三、当周检索顺序

按这个顺序跑，跑完就停，不无限加网站：

1. 城市资料里记的主办方清单，逐个看当周推文或公告。
2. 本地官方发布，看本周新增。
3. 目标日期那一周的时间范围，搜「城市 ＋ 本周活动」「城市 ＋ 周末 亲子」。
4. 对前一步找到的每个候选，回主办方页核起止日与预约。

**只跑一轮直接核证加一个替代入口。** 还没解，就换核心活动或说明缺什么，不靠不断加网站拖延输出。

## 四、三态与判定

每个活动记三态：

| 态 | 判据 | 处理 |
|---|---|---|
| **当周在办** | 主办方原始页给出起止日且覆盖目标日 | 可作主菜 |
| **期外** | 已结束，或开始日晚于目标日 | 不作候选 |
| **期限不明** | 只有「持续至 X 旬」「火热进行中」 | 不进主菜；可作备选并注明需自查 |

**多篇互抄同一句「持续至 X 月下旬」算一个证据根**，不作期限证明。

## 五、查不到怎么办

不编活动。写实三句：

> 当周活动未查到。可能原因：主办方未提前发布，或该城公开渠道以小程序为主。
> 自查三条：① 场馆官方公众号近七天的推送 ② 当地文旅局公众号本周发布 ③ 目标场馆小程序的活动页。
> 本方案按常设内容排，不含限时活动。

## 六、城市资料里存什么

不存活动，存渠道。每个城市记：

- 主要场馆名单，含各自的主办公众号或小程序名。
- 本地官方发布渠道，两到三个。
- 一城一源的天气主源。
- 已知的坑，例如同名的两处场馆、需提前多久放票。

字段见 `city/city-profile.template.json` 的 `activity_sources`。

## 七、跨城时的注意

换城市后，前三件事先核：天气主源、限行规则、场馆预约机制。这三样各城差别最大，也最容易让人白跑。

票价与场次一律重查，不沿用别的城市经验。
